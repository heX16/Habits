ЭТАП 0. Подготовка контекста
1. Прочитать `web/readme_for_gpt.md` целиком. Сохранить ключевые сущности (таблицы БД, эндпоинты, параметры привычек, статусы, UI-механики) в краткую «память» для быстрых ссылок.  
2. Убедиться, что правила пользователя («комментарии и commit-сообщения на английском») занесены в долговременную память, если ещё не сохранены.

ЭТАП 1. Полный инвентаризационный срез существующего проекта  
(цель — создать точную карту кода, на которую будем ссылаться дальше)

1. С помощью инструмента «list directory» вывести дерево проекта.  
2. Для каждого исходного файла:
   • Python — найти все `def`, `class`, `@app.route`, вспомогательные функции.  
   • JavaScript — найти все `function`, стрелочные функции, обработчики событий.  
   • HTML/CSS — зафиксировать id / class, привязанные скрипты, высокоуровневые секции.  
   Итог: таблица «Файл → функции/классы/ключевые элементы».  
3. Сохранить результаты как структурированные данные (JSON/Markdown таблица) для повторного использования.

ЭТАП 2. Каталог функциональности пользовательского интерфейса  
1. Проанализировать:
   • `templates/*.html` — макеты страниц.  
   • `static/*.js` — поведение (renderTable, handleCellClick и т.д.).  
   • `static/style.css` — визуальные особенности, темы.  
2. Сформировать список всех UI-функций и взаимодействий в свободном от кода виде: «Что делает пользователь, какой эффект видит, какие данные отправляются/получаются».  
3. Укрупнить в категории: Main page, Habit page, Options page, Notifications, etc.

ЭТАП 3. Оценка повторного использования кода  
1. Пометить файлы/функции, которые могут быть перенесены без изменений:
   • Чистая бизнес-логика (например, `habits_database.py`, части `habits_core.py`).  
   • Универсальные утилиты (status_mapping, CSV-экспорт/импорт).  
2. Отметить, какие модули потребуют адаптации, а какие лучше переписать (в первую очередь HTTP-эндпоинты и фронтенд-JS).

ЭТАП 4. Проектирование новой архитектуры на Kivy  
1. Слои приложения:  
   • Data Layer — неизменный SQLite + `HabitsDatabase`.  
   • Domain Logic — адаптированная `habits_core`.  
   • UI Layer (Kivy): экраны (ScreenManager)  
        – MainTrackerScreen  
        – HabitScreen  
        – OptionsScreen  
        – Dialogs/Popups (StatusMenu, ConfirmDelete, Notifications)  
   • Services — планировщик полуночного обновления, экспорт/импорт, платформенные шлюзы (Android storage permissions, Windows tray).  
2. Развести ответственность по пакетам: `models/`, `services/`, `screens/`, `widgets/`, `assets/`.

ЭТАП 5. Мэппинг старых функций на новую архитектуру  
1. Для каждого UI-функционала из ЭТАПА 2 указать:

2. Сохранить таблицу «Фча → Новый эквивалент» для пошаговой реализации.

ЭТАП 6. Выявление недостающих функций  
1. Что исчезает при уходе от браузера (кеширование, Jinja2, fetch API) — спроектировать альтернативы: локальный кэш, Python-события, etc.

ЭТАП 8. Организация последовательной работы GPT-агента  
(мета-процесс, чтобы агент уверенно шёл от простого к сложному)

1. На каждом крупном шаге:
   a) перечислить инструментальные вызовы (list_dir, grep_search, read_file, edit_file).  
   b) сформировать ожидаемый вывод/изменение.  
2. Чётко отделять этапы анализа от этапов изменения кода.  
3. Поддерживать «рабочую память» — резюмировать, что уже сделано и что осталось.  
4. Делать минимальные атомарные правки, сразу проверять linter / runtime.  
5. Регулярно пересматривать список задач, переносить выполненные в «Done».

ЭТАП 9. Контрольные точки & критерии готовности  
• MVP — реплика веб-функционала на десктопе Windows.  
• Далее — адаптация ввода/жестов и упаковка в APK для Android.
